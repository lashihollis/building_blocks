# Lesson 7 Solutions: Healthcare Analytics Case Study

## Practice Problem 1

### Business Question

Operations wants to know how busy each specialty was during July.

Return:

- Specialty
- Total number of visits

Sort from the busiest specialty to the least busy.

### Solution

```sql
SELECT
    p.specialty,
    COUNT(v.visit_id) AS total_visits
FROM visits v
JOIN providers p
    ON v.provider_id = p.provider_id
WHERE v.visit_date BETWEEN '2026-07-01' AND '2026-07-31'
GROUP BY p.specialty
ORDER BY total_visits DESC;
```

### Why This Works

- We start with the `visits` table because each row represents one visit.
- We join `providers` to access the provider's specialty.
- We filter to July before aggregating.
- We group by specialty to count all visits for each specialty.

## Practice Problem 2

### Business Question

Marketing wants to identify returning patients.

Return:

- Patient ID
- Number of visits

Only include patients with more than one visit.

Sort by the highest number of visits.

### Solution

```sql
SELECT
    patient_id,
    COUNT(*) AS visit_count
FROM visits
GROUP BY patient_id
HAVING COUNT(*) > 1
ORDER BY visit_count DESC;
```

### Why This Works

- We group visits by patient.
- `COUNT(*)` tells us how many visits each patient had.
- `HAVING` filters after the aggregation, returning only patients with multiple visits.
- Results are sorted from the most visits to the fewest.

# 🏆 Challenge Solution

### Business Question

Leadership wants a Provider Performance Report containing:

- Provider Name
- Specialty
- Total Visits
- Unique Patients
- Total Revenue
- Average Revenue per Visit

### Solution

```sql
WITH provider_metrics AS (

    SELECT
        v.provider_id,
        COUNT(v.visit_id) AS total_visits,
        COUNT(DISTINCT v.patient_id) AS unique_patients,
        SUM(v.revenue) AS total_revenue,
        AVG(v.revenue) AS avg_revenue_per_visit
    FROM visits v
    GROUP BY v.provider_id

)

SELECT
    p.provider_name,
    p.specialty,
    pm.total_visits,
    pm.unique_patients,
    pm.total_revenue,
    ROUND(pm.avg_revenue_per_visit, 2) AS avg_revenue_per_visit
FROM provider_metrics pm
JOIN providers p
    ON pm.provider_id = p.provider_id
ORDER BY pm.total_revenue DESC;
```

### Why This Works

This solution separates the problem into two logical steps.

**Step 1**

The CTE calculates all provider-level metrics from the `visits` table.

This includes:

- Total visits
- Unique patients
- Total revenue
- Average revenue per visit

At this point, we only need the `visits` table because it already contains the information required for every calculation.

**Step 2**

Once the metrics are calculated, we join the `providers` table to add descriptive information like provider name and specialty.

This keeps the query easier to read and avoids unnecessary joins while calculating metrics.

## Analytics Engineer Review

Before writing the SQL, ask yourself:

✅ What should one row represent?

> One provider.

✅ Which table should I start from?

> The `visits` table, because it contains the facts we're measuring.

✅ Which tables do I actually need?

> `visits` for the metrics and `providers` for descriptive information.

✅ When should I aggregate?

> Before joining to the dimension table.

✅ Could any joins duplicate rows?

> No. Each provider has one matching record in the `providers` table, making this a one-to-one join after aggregation.

# Key Takeaways

- Start with the business question.
- Think about the grain of your output before writing SQL.
- Build metrics from the fact table whenever possible.
- Join dimension tables only when you need descriptive attributes.
- Organize complex logic with CTEs to improve readability.
- Great Analytics Engineers write SQL that is easy to understand, validate, and maintain.
