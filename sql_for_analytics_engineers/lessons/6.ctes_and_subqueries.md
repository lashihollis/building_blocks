Both CTEs and subqueries can produce the same result.

---

## What is a CTE?

A Common Table Expression (CTE) creates a temporary named result set that exists only for the duration of a query.

Think of a CTE as giving a step in your analysis a name.

Instead of writing one giant SQL statement, you build your logic one step at a time.

```sql
WITH visits AS (

    SELECT *
    FROM patient_visits

)

SELECT *
FROM visits;
```

---

## What is a Subquery?

A subquery is simply a query nested inside another query.

Like CTEs, subqueries allow you to build on the results of another query—they're just written differently.

```sql
SELECT *

FROM (

    SELECT *
    FROM patient_visits

) visits;
```

Both approaches return the same result.

The difference is how easy the query is to read and maintain.

---

## CTE vs. Subquery

Let's answer a simple business question.

> **Business Question**
>
> Which providers have generated more than $10,000 in total revenue?

First, we need to calculate each provider's total revenue.

Then we can filter the results.

### Using a CTE

```sql
WITH provider_revenue AS (

    SELECT
        provider_id,
        SUM(revenue) AS total_revenue

    FROM patient_visits

    GROUP BY provider_id

)

SELECT *

FROM provider_revenue

WHERE total_revenue > 10000;
```

The CTE clearly separates the calculation from the filtering.

---

### Using a Subquery

```sql
SELECT *

FROM (

    SELECT
        provider_id,
        SUM(revenue) AS total_revenue

    FROM patient_visits

    GROUP BY provider_id

) provider_revenue

WHERE total_revenue > 10000;
```

Both queries return the same result.

As queries become more complex, CTEs are generally easier to read because each step has a descriptive name.

---

## Why Analytics Engineers Prefer CTEs

Imagine your stakeholder comes back and says:

> "Can we also include the number of visits for each provider?"

With a CTE, you simply update the calculation step.

```sql
WITH provider_revenue AS (

    SELECT
        provider_id,
        COUNT(*) AS visit_count,
        SUM(revenue) AS total_revenue

    FROM patient_visits

    GROUP BY provider_id

)

SELECT *

FROM provider_revenue;
```

You don't need to rewrite the rest of the query.

As business logic grows, CTEs make SQL much easier to extend.

## Chaining Multiple CTEs

Let's answer another business question.

> **Business Question**
>
> Which providers generated the most revenue, and how do they rank compared to every other provider?

There are two steps:

1. Calculate total revenue for each provider.
2. Rank providers from highest to lowest revenue.

Instead of trying to solve everything in one query, we'll create one CTE for each step.

```sql
WITH provider_revenue AS (

    SELECT
        provider_id,
        SUM(revenue) AS total_revenue

    FROM patient_visits

    GROUP BY provider_id

),

provider_rank AS (

    SELECT
        provider_id,
        total_revenue,
        RANK() OVER (
            ORDER BY total_revenue DESC
        ) AS revenue_rank

    FROM provider_revenue

)

SELECT *

FROM provider_rank

WHERE revenue_rank <= 5;
```

Notice how each CTE has a single responsibility.

**provider_revenue**
- Calculates total revenue by provider.

**provider_rank**
- Ranks providers based on that revenue.

Finally, the main query returns the top 5 providers.

This step-by-step approach makes the SQL much easier to read, test, and modify.

## When is a Subquery a Good Choice?

CTEs aren't always the best solution.

Sometimes a subquery is simpler.

Let's answer another business question.

> **Business Question**
>
> Which patient visits generated more revenue than the average visit?

To answer this, we first need to know the overall average visit revenue.

That value is only needed once, making a subquery a good fit.

```sql
SELECT
    patient_id,
    visit_id,
    revenue

FROM patient_visits

WHERE revenue >

(

    SELECT AVG(revenue)
    FROM patient_visits

);
```

The subquery calculates the average revenue across all visits.

The outer query then returns only visits that exceed that average.

Since the calculation is short and only used once, a subquery keeps the SQL concise.

---

## Additional Thought

It's okay to use `SELECT *` from a CTE when:

- The CTE defines exactly the columns you want.
- The schema is unlikely to change.
- You're using the CTE as an intermediate transformation step.

Many Analytics Engineers do this to avoid repeating long column lists throughout a query.

Be more intentional about selecting columns in your final output, where you control exactly what downstream users receive.

## Key Takeaways

- CTEs and subqueries can often solve the same problem.
- CTEs usually make complex SQL easier to read and maintain.
- Subqueries are great for short calculations used only once.
- Break large problems into small, logical steps.
- Good SQL isn't just correct—it tells a story that other engineers can follow.
