# Think Like an Analytics Engineer

Most SQL mistakes aren't syntax mistakes.

They're relationship mistakes.

Experienced Analytics Engineers don't ask:

> "How do I write this JOIN?"

They ask:

> "How are these tables related, and what should one row represent in my final result?"

Understanding the business question should determine your join—not the other way around.

---

# Why Do We Need Joins?

Most databases are normalized.

Instead of storing everything in one massive table, related information is separated into multiple tables.

### patients

| patient_id | first_name | last_name |
|------------|------------|-----------|

### visits

| visit_id | patient_id | provider_id | visit_date |
|----------|------------|-------------|------------|

### providers

| provider_id | provider_name | specialty |
|-------------|---------------|-----------|

Each table has one responsibility.

To answer business questions, we combine those tables using joins.

---

# Primary Keys vs. Foreign Keys

A **Primary Key** uniquely identifies a row.

Examples:

- patient_id
- visit_id
- provider_id

A **Foreign Key** references a primary key in another table.

Example:

```text
visits.patient_id
        ↓
patients.patient_id
```

These relationships allow SQL to connect tables together.

---

# What is a JOIN?

A JOIN combines rows from two or more tables using a shared key.

The type of join you choose depends on the business question you're trying to answer.

---

# Join Types

## INNER JOIN

Returns only matching rows from both tables.

**Use when:** You only care about records that exist in both tables.

**Example Business Question:**

> Show every visit along with the patient's name.

**Why?**

Every row should represent a valid visit. If a visit doesn't have a matching patient, it's likely a data quality issue.

---

## LEFT JOIN

Returns every row from the left table and matching rows from the right table.

Missing matches become `NULL`.

**Use when:** You want to keep every record from your starting table.

**Example Business Question:**

> Show every patient, including patients who have never had a visit.

**Why?**

The business wants every patient represented, even if they haven't visited yet.

---

## RIGHT JOIN

Returns every row from the right table.

Most Analytics Engineers prefer rewriting these as LEFT JOINs because they're easier to read.

---

## FULL OUTER JOIN

Returns every row from both tables.

Useful when comparing or reconciling datasets.

---

# Before You Write SQL

Before every join, ask yourself:

1. What should one row represent?
2. Which table should I start with?
3. Which join type answers the business question?
4. Why?

---

# Worked Example 1

## Business Question

Show every visit along with the patient's first name.

### What should one row represent?

One visit.

### Starting table

visits

### Join type

INNER JOIN

### Why?

Every visit should have a matching patient.

### SQL

```sql
SELECT
    p.first_name,
    v.visit_date
FROM visits v
INNER JOIN patients p
    ON v.patient_id = p.patient_id;
```

---

# Worked Example 2

## Business Question

Show every patient, even if they have never had a visit.

### What should one row represent?

One patient.

### Starting table

patients

### Join type

LEFT JOIN

### Why?

The business wants every patient included.

### SQL

```sql
SELECT
    p.first_name,
    p.last_name,
    v.visit_date
FROM patients p
LEFT JOIN visits v
    ON p.patient_id = v.patient_id;
```

---

# Worked Example 3

## Business Question

Show each visit with the patient name and provider name.

### What should one row represent?

One visit.

### Starting table

visits

### Join type

INNER JOIN

### Why?

We're enriching each visit with related information.

### SQL

```sql
SELECT
    p.first_name,
    pr.provider_name,
    v.visit_date
FROM visits v
INNER JOIN patients p
    ON v.patient_id = p.patient_id
INNER JOIN providers pr
    ON v.provider_id = pr.provider_id;
```

# Accidental Duplication

One of the most common SQL mistakes is joining tables on the wrong key.

Suppose a patient has:

- 3 visits
- 5 claims

If you join on `patient_id`:

```sql
SELECT *
FROM visits v
INNER JOIN claims c
    ON v.patient_id = c.patient_id;
```

Every visit matches every claim for that patient.

Instead of 5 claim records, you now have 15 rows.

The SQL is valid.

The join isn't.

### Correct Join

A claim belongs to a specific visit, so `visit_id` is the correct business key.

```sql
SELECT
    v.visit_id,
    v.visit_date,
    c.claim_id,
    c.amount
FROM visits v
INNER JOIN claims c
    ON v.visit_id = c.visit_id;
```

**Analytics Engineer Tip**

Don't join on what matches.

Join on what relates.

---

# Validate Your Join

Before trusting your results, ask yourself:

- Did my row count unexpectedly increase?
- Did rows disappear?
- Does each row still represent what I expect?
- Am I joining on the correct business key?

Good Analytics Engineers validate their joins before moving on.
