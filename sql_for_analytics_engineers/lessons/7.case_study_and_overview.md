## 🧠 Think Like an Analytics Engineer

Real analytics work rarely starts with SQL.

It starts with business questions.

Your job is to translate those questions into reliable datasets.

Before writing SQL, ask yourself:

- What metric am I calculating?
- What should one row represent?
- Which table should I start from?
- Which joins are required?
- Could any joins duplicate rows?
- What business rules should I apply before calculating my metrics?

The SQL is usually the easy part.

Designing the solution is where Analytics Engineers provide value.

## Worked Example 1

### Business Question

How much revenue did each provider generate during July?

### Think Through It

Revenue lives in the **visits** table.

Provider names live in the **providers** table.

Each visit belongs to exactly one provider.

That means we should:

1. Start with the visits table.
2. Join providers.
3. Filter to July.
4. Aggregate revenue by provider.

```sql
SELECT
    p.provider_name,
    SUM(v.revenue) AS total_revenue
FROM visits v
JOIN providers p
    ON v.provider_id = p.provider_id
WHERE v.visit_date BETWEEN '2026-07-01' AND '2026-07-31'
GROUP BY p.provider_name
ORDER BY total_revenue DESC;
```

**Why this works**

- We start from the fact table.
- We only join the table we need.
- We filter before aggregating.
- One row represents one provider.

## Worked Example 2

### Business Question

Leadership wants to know how many unique patients each provider treated.

### Think Through It

A patient may visit the same provider multiple times.

Leadership wants patients—not visits.

That means we need to count distinct patient IDs.

```sql
SELECT
    p.provider_name,
    COUNT(DISTINCT v.patient_id) AS unique_patients
FROM visits v
JOIN providers p
    ON v.provider_id = p.provider_id
GROUP BY p.provider_name
ORDER BY unique_patients DESC;
```

**Why this works**

Without `DISTINCT`, we'd count repeat visits instead of unique patients.

Always confirm what the business is actually asking you to count.

## Worked Example 3

### Business Question

Finance wants a report showing every unpaid claim along with the patient and provider responsible for the visit.

### Think Through It

Claims contain the payment information.

Visits connect patients and providers.

We'll use the visits table to bridge everything together.

```sql
SELECT
    c.claim_id,
    p.patient_name,
    pr.provider_name,
    c.amount
FROM claims c
JOIN visits v
    ON c.visit_id = v.visit_id
JOIN patients p
    ON v.patient_id = p.patient_id
JOIN providers pr
    ON v.provider_id = pr.provider_id
WHERE c.status = 'Unpaid'
ORDER BY c.amount DESC;
```

**Why this works**

Each join follows the relationships between tables.

We never guess how tables connect—we use the appropriate keys.

## Key Takeaways

✔ Start with the business question—not the SQL.

✔ Understand the grain of every table.

✔ Start from the fact table whenever possible.

✔ Join only the tables you need.

✔ Aggregate only after you've built the correct dataset.

✔ Use CTEs to organize complex logic.

✔ Great SQL isn't clever.

It's readable, maintainable, and produces trustworthy results.
